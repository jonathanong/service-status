# Adapters: cheapest ways to read a status endpoint

Every recipe below was run against the real entry named in its heading on 2026-11-11 (plain `curl`, `jq`, `iconv`, `sed`). Sizes come from `verification.json`, which is regenerated by re-fetching every URL in `services.json`:

- **raw** = body bytes with plain `curl` (no `Accept-Encoding`).
- **gzip** = bytes on the wire with `-H 'Accept-Encoding: gzip'` (what `curl --compressed` costs).

Two questions per adapter: (a) is anything wrong right now, (b) which component or incident.

Rules of thumb:

1. Start with the `status` endpoint (about 200 bytes where it exists).
2. If it is not "all clear", fetch the smallest endpoint that names the incident.
3. Send `--compressed` unless the table says the server ignores it. Several servers compress JSON and RSS but not Atom.
4. Use `curl -r 0-N` (HTTP Range) to read only the head of an Atom/RSS feed. It works on Atlassian Statuspage and Google status pages. It does not work on Better Stack, AWS, Fastly or DeepSeek (those return 200 with the full body), and Atlassian ignores Range when gzip is also requested.

## statuspage (GitHub)

```sh
# (a) 215 bytes. indicator: none | minor | major | critical | maintenance
curl -s https://www.githubstatus.com/api/v2/status.json | jq -r '.status.indicator'
# -> none

# (b) active incidents only (160 bytes when empty). Cloudflare right now returns 3, ~6.6KB:
curl -s https://www.cloudflarestatus.com/api/v2/incidents/unresolved.json \
  | jq -r '.incidents[]|[.impact,.status,.name,([.components[]?.name]|join(","))]|@tsv'
# -> minor  identified  Replicate Input Upload Issue  Replicate

# (b) component-level view, only if you need it. Drop group rows and filter by name:
curl -s --compressed https://status.sentry.io/api/v2/summary.json \
  | jq -r '.components[]|select(.group==false and .status!="operational")|"\(.status)\t\(.name)"'
# -> under_maintenance  EU Error Ingestion

# (b) history head: only the newest ~5.5KB of a 69,605-byte feed (Range works; it is 2,048 with -r 0-2047)
curl -s -r 0-5999 https://www.githubstatus.com/history.atom \
  | sed -n '/<entry>/,$p' | grep -oE '<(published|title)>[^<]*' | head -4
# <entry><content> starts with "Resolved", "Monitoring", "Identified" or "Investigating" (HTML-escaped).
```

Size picture (raw / gzip), from `verification.json`:

| endpoint                    | github          | anthropic       | stripe          | cloudflare       | twilio           |
| --------------------------- | --------------- | --------------- | --------------- | ---------------- | ---------------- |
| `status.json`               | 215 / 215       | 212 / 212       | 215 / 215       | 235 / 235        | 233 / 233        |
| `incidents/unresolved.json` | 160 / 160       | 157 / 157       | 160 / 160       | 6,659 / 1,781    | 43,020 / 3,957   |
| `summary.json`              | 4,310 / 1,125   | 3,787 / 927     | 44,386 / 4,591  | 226,659 / 39,078 | 210,767 / 23,521 |
| `history.atom`              | 69,605 / 69,605 | 39,265 / 39,265 | 26,063 / 26,063 | 28,757 / 2,170   | 29,738 / 29,738  |
| `history.rss`               | 71,592 / 10,139 | 39,588 / 5,329  | 27,950 / 2,122  | 29,058 / 2,150   | 31,456 / 3,143   |

Note the Atom vs RSS gap: GitHub, Anthropic, Stripe and Twilio do not gzip `history.atom` but do gzip `history.rss`. If you need the whole feed, take the RSS. If you only need the head, use `curl -r` on Atom (no gzip header).

Incident impact values: `none`, `minor`, `major`, `critical`. Component `status` values: `operational`, `degraded_performance`, `partial_outage`, `major_outage`, `under_maintenance`.

## incidentio (OpenAI, Linear, Docker Hub, ...)

These pages (served from Vercel, no `x-statuspage-version` header) expose a Statuspage-shaped compatibility API, but only part of it. Verified on all 31 entries: `status.json`, `summary.json` (components only, no incidents), `history.atom`, `history.rss` and `proxy`. `/api/v2/incidents/unresolved.json` does not exist here: it returns HTTP 404 with a ~296KB HTML page. Never call it.

```sh
# (a) 202 bytes. OpenAI at the time of testing: {"description":"Major System Outage","indicator":"critical"}
curl -s https://status.openai.com/api/v2/status.json | jq -c .status

# (b) incident names. "proxy" is the JSON the page itself loads (undocumented, so it may change):
#     13,150 raw / 3,061 gzip for openai; 3,655 / 1,057 for linear.
curl -s --compressed https://status.openai.com/proxy/status.openai.com \
  | jq -r '.summary.ongoing_incidents[]|[.status,.name]|@tsv'
# -> investigating  Unable to start new Workspace Agent runs
#    (.summary.affected_components[].component_id joins to .summary.components[].id for names)
```

The proxy path is `{statusPage}/proxy/{host of statusPage}`. If the proxy ever breaks, fall back to `history.rss` (OpenAI: 97,509 raw / 8,756 gzip) read with `head -c`.

PostHog is also on incident.io but has no compat API and no proxy; it is `feed-only` (`feed.atom`, 32,272 bytes, ignores gzip).

## instatus (Deno, Koyeb, Northflank)

```sh
# (a) Deno: 69 bytes. status: UP | HASISSUES | UNDERMAINTENANCE
curl -s https://denostatus.com/summary.json | jq -r .page.status
# -> UP

# (b) Northflank and Koyeb summary.json also carry the incident lists:
curl -s https://status.northflank.com/summary.json \
  | jq -c '{s:.page.status,a:[.activeIncidents[]?|{name,impact,status}]}'
# -> {"s":"HASISSUES","a":[{"name":"Security incident","impact":"MAJOROUTAGE","status":"MONITORING"}]}
# Koyeb has recentlyResolvedIncidents (611 raw / 339 gzip); Deno's summary does not list incidents.

# (b) component states (Koyeb 2,655 / 790; Deno 3,423 / 988)
curl -s --compressed https://status.koyeb.com/v2/components.json | jq -c '.components[]|select(.status!="OPERATIONAL")|{name,status}'
```

Deno also has `history.atom` (35,764 / 6,171) and `history.rss`.

## betterstack (Hugging Face, Modal, Turso)

`index.json` is JSON:API and big (77KB, 124KB and 273KB raw). `aggregate_state` sits in the first few hundred bytes. Range is not honoured, and closing the pipe early still transfers about 32KB, so rely on gzip instead.

```sh
# (a) 4,531 bytes on the wire for Hugging Face (8,662 for Turso, 5,726 for Modal)
curl -s --compressed https://status.huggingface.co/index.json | head -c 1500 | grep -o '"aggregate_state":"[a-z_]*"'
# -> "aggregate_state":"operational"       (also: degraded | downtime | maintenance)

# (b) feed.atom is really RSS 2.0 (<item>, not <entry>). 4,274 bytes gzip for Hugging Face.
curl -s --compressed https://status.huggingface.co/feed.atom | grep -oE '<(title|pubDate)>[^<]*' | sed -n '2,5p'
```

Feed items include scheduled maintenance as well as incidents.

## statusio (GitLab, Neon)

```sh
# (a) 11,354 raw / 1,343 gzip for GitLab. status_code 100 = operational
curl -s --compressed https://api.status.io/1.0/status/5b36dc6502d06804c08349f7 | jq -c .result.status_overall
# -> {"updated":"...","status":"Operational","status_code":100}

# (b) components that are not 100, plus open incidents and maintenance:
curl -s --compressed https://api.status.io/1.0/status/5b36dc6502d06804c08349f7 \
  | jq -c '{bad:[.result.status[]|select(.status_code!=100)|.name],incidents:.result.incidents,maint:(.result.maintenance|length)}'
# GitLab names: Git Operations, API, CI/CD, Package Registry, Container Registry, GitLab Pages, Website, ...
```

The `rss` endpoint (`/pages/{id}/rss`, ~16KB) holds history, not state. Neon's document is 26,397 raw / 1,512 gzip.

## aws

`https://health.aws.amazon.com/public/currentevents` is UTF-16 (big-endian, BOM `FEFF`). `Content-Type: application/json;charset=utf-16`. `jq` cannot read it directly: pipe through `iconv -f UTF-16 -t UTF-8`. It is 276,712 raw / 28,362 gzip and contains the full event log in many languages, so filter hard.

```sh
# (a)+(b) active events only: status "0" = resolved, anything else is open
# (1 = informational, 2 = degraded, 3 = disruption)
curl -s --compressed https://health.aws.amazon.com/public/currentevents | iconv -f UTF-16 -t UTF-8 \
  | jq -r '.[]|select(.status!="0")|[.status,.service,.region_name,.summary,(.date|tonumber|todate)]|@tsv'
# -> 3  multipleservices-me-central-1  UAE  Region Availability  2026-03-01T12:51:25Z

# Filter by region or service: select(.service|test("ec2-us-east-1"))  (service = "<product>-<region>")

# Cheapest per-service check: one RSS file per service-region (719 bytes when healthy, no <item> children).
# The slug is the .service value above. A bogus slug is a clean 404 (23 bytes), not a catch-all 200.
curl -s https://status.aws.amazon.com/rss/ec2-us-east-1.rss | grep -c '<item>'
# -> 0
```

`https://status.aws.amazon.com/rss/all.rss` (70,758 raw, no gzip) lists recent events across all services, including resolved ones ("Service is operating normally: [RESOLVED] ..."). `status.aws.amazon.com/data.json` is an alias of `currentevents`.

Gotcha: events can stay open for months. At testing time two "Region Availability" events (me-central-1, me-south-1) had been status 3 since March 2026. Do not treat an open event as "now" without checking the region.

## gcp (Google Cloud, Firebase)

`incidents.json` is 292,106 raw / 53,186 gzip (Firebase: 79,576 / 13,390). It is a JSON array, newest `begin` first, with Range support.

```sh
# (a) cheapest: 2KB of the Atom feed (newest first; titles start with RESOLVED: when closed)
curl -s -r 0-3999 https://status.cloud.google.com/feed.atom | sed -n '/<entry>/,$p' | grep -oE '<(updated|title)>[^<]*' | head -4

# (a)+(b) authoritative: active = no end timestamp
curl -s --compressed https://status.cloud.google.com/incidents.json \
  | jq -c '[.[]|select(.end==null)|{service_name,severity,begin,uri,products:[.affected_products[].title]}]'
# -> []   (0 active at testing time)
# Filter by region: select(any(.currently_affected_locations[]?; .id=="us-central1"))   (locations look like {"title":"London (europe-west2)","id":"europe-west2"})
```

`products.json` (23,109 / 7,145) is the product list for the `components` key (top-level object with `products`). Firebase has `feed.atom` too (1,226 raw, 574 gzip).

## feed-only (DeepSeek, OpenRouter, PostHog, Hetzner, Fastly)

No state endpoint exists, so the newest entry is the answer. Use Range where honoured; otherwise pipe through `head -c`.

```sh
# OpenRouter history.atom (9,512 raw / 2,276 gzip): newest entries first
curl -s --compressed https://status.openrouter.ai/history.atom | sed -n '/<entry>/,$p' | grep -oE '<(updated|title)>[^<]*' | head -4
# DeepSeek feed.atom (16,488 bytes, no gzip, no Range): titles are bilingual
curl -s https://status.deepseek.com/feed.atom | head -c 3000 | grep -oE '<(updated|title)>[^<]*' | head -4
# Fastly rss (StatusCast): 98,149 bytes, no gzip, no Range
curl -s https://www.fastlystatus.com/rss | head -c 4000
```

An entry is "current" only if its body says it is not resolved. A recent `<updated>` alone does not tell you that.

## Gotchas

- **Cloudflare components are mostly data centres.** `summary.json` is ~225KB and ~66 components were non-operational at testing time, almost all "City, Country - (XXX)" data-centre rows in routine maintenance. Use `status.json` and `unresolved.json`, and pick named products (Workers, R2, Pages, ...). Replicate is a Cloudflare component now.
- **Atlassian umbrella vs product pages.** `status.atlassian.com` mostly reports cross-product incidents; Jira, Confluence, Bitbucket and Trello each have their own page in this directory.
- **GitHub has one page for everything.** Actions, Pages, Packages and Copilot are components, not separate entries.
- **Status pages lag real outages**, often by 10 to 30 minutes, and some vendors only post major ones. A green page does not clear the vendor; a red one is strong evidence.
- **Statuspage `indicator: none` can coexist with a scheduled maintenance** (`maintenance` indicator) and with per-component degradation. Check the component you depend on.
- **incident.io pages are not full Statuspage.** No `unresolved.json` (404 plus ~296KB HTML), and `summary.json` has no incidents array. Use `proxy`.
- **Better Stack `index.json` is large** and Range is ignored; gzip it and read the first bytes.
- **AWS is UTF-16**, 276KB, multilingual, and includes long-open regional events.
- **Some human pages return 403 to non-browser clients** (Mistral, Fastly). Their JSON API or feed URLs in the directory were verified with plain `curl`.
- **Local DNS filters can null-route status hosts.** `status.datadoghq.com`, `status.newrelic.com` and `status.bugsnag.com` resolved to `0.0.0.0` on the machine that built this directory. The entries use the vendor's `*.statuspage.io` hostnames instead, and `page.url` in those responses confirms the vanity domain. A connect error to a status host is not an outage.
- **Redirecting hostnames.** `status.quay.io`, `status.semaphoreci.com`, `status.codecov.io`, `status.zoom.us`, `status.prisma.io` and others redirect; the directory lists the final URL, so a missing `-L` is fine.
- **Bad bots.** Do not set a fake browser User-Agent to get past a 403; drop the entry or use another endpoint. `status.x.ai` (also what `status.cursor.com` redirects to) returns 403 to curl and is not in the directory.
- **Plain `curl -s -m 10` is enough** for every endpoint in `services.json`: none needs special headers (`verification.json` was produced that way). Add `--compressed` for fewer bytes.
